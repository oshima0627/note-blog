# Claude Codeの既定が8月14日からautoモードに

※本記事は **2026年8月8日時点** の公開情報にもとづきます。料金・仕様は変わりやすいため、最新は公式ドキュメントでご確認ください。

この記事でわかること：

- 2026年8月14日から、Claude Codeの既定の権限モードがPro/Max/Teamで「auto」に変わること
- autoモードで自動的に通る操作と、既定でブロックされる操作
- 手動承認（Manual）のまま使い続けたい場合に、いま何を設定すればよいか

## 何が変わるのか

Anthropicは2026年8月7日、Claude Codeの既定の権限モードを **auto** に切り替えると発表しました。適用は **2026年8月14日** からで、対象は **Pro / Max / Team プランの新規セッション** です。

autoモードは、ツール呼び出しのたびに人へ確認を出す代わりに、**別の分類器（classifier）モデル**が実行前に各アクションを審査する仕組みです。依頼の範囲を超えるもの、認識されていないインフラを対象にするもの、Claudeが読み込んだ敵対的なコンテンツに誘導された疑いがあるものをブロックします。

Claude Enterprise・Claude API・Claude Platform on AWS・Amazon Bedrock・Google CloudのAgent Platform・Microsoft Foundry では、当面オプトイン（自分で有効化する方式）のままとされています。

**読者への影響**：Pro/Max/Teamを使っていて自分で既定モードを設定していない人は、8月14日以降、新しいセッションが自動的にautoモードで始まります。公式ドキュメントによれば、自分で既定を設定している場合は、一度だけ表示される切り替えの確認を承諾しない限りそのままです。組織が管理している既定も変わりません。

なお、分類器の追加トークン分について、Pro/Max/Teamでは課金しなくなったことも同時に告知されています。

## Anthropicが示した数字

切り替えの根拠として、次の比較が公開されています。

- 1,053件の検証のうち、テスターが危険なコマンドに気づいたのは **143件（13.6%）**。autoモードは同じコマンドのうち **937件（89%）** をブロック
- 深刻度7以上で見ると、手動承認のセッションの **6.3%** に「ユーザーが明示的に依頼していない有害な操作」が含まれたのに対し、autoモードのセッションでは **2.4%**
- 第三者（Apollo）による再テストでは、対策強化後に分類器の見逃し率が **12%から7%** に低下

エンジニアリング解説によれば、分類器は**ユーザーのメッセージとエージェントのツール呼び出しだけ**を見て判断し、Claude自身の発言やツールの出力は除去されます。Claudeが「これは安全です」と説得して承認を得る経路を断つための設計です。ツール結果側には、サーバー側の別プローブが警告を差し込む層が用意されています。

## 既定でブロックされる操作・通る操作

公式ドキュメントに列挙されているもののうち、個人開発者に関係が深いものを抜き出します。

**既定でブロックされる主なもの**

- `curl | bash` のような、ダウンロードしたコードの実行
- 機微なデータの外部エンドポイントへの送信
- 本番デプロイ、マイグレーション、クラウドストレージの大量削除
- IAMやリポジトリ権限の付与、共有インフラの変更
- セッション開始前から存在していたファイルの不可逆な削除、force push
- `git reset --hard` / `git checkout -- .` / `git clean -fd` / `git stash drop` など、未コミットの変更を捨てると推定される操作
- このセッションで作られたのではないコミットへの `git commit --amend`
- `terraform destroy` / `pulumi destroy` / `cdk destroy` など、リソースを破壊するプラン適用

**既定で通る主なもの**

- 作業ディレクトリ内のローカルファイル操作
- ロックファイルやマニフェストに宣言済みの依存関係のインストール
- `.env` を読み、対応するAPIへ認証情報を送ること
- 読み取り専用のHTTPリクエスト
- 作業中リポジトリの任意のブランチへのpush（ただし `production` や `gh-pages` のように公開・デプロイ先を示す名前のブランチは個別判断）

**読者への影響**：「確認が減る」だけでなく「push が確認なしで通る」点が実務上は大きい変化です。人のチェックポイントを残したい操作には、`permissions.ask` ルールを明示的に足しておくのが確実です。

会話中に「pushしないで」「レビューするまで待って」と伝えた境界も、分類器はブロック信号として扱います。ただしこれはルールとして保存されるわけではなく、毎回トランスクリプトから読み直される仕組みのため、コンテキストの圧縮でその発言が消えると失われる可能性があります。確実に止めたい操作は `deny` ルールで書くのが安全です。

## 止まりすぎたときの挙動

分類器が **3回連続** または **合計20回** ブロックすると、autoモードは一時停止し、通常の承認プロンプトに戻ります。プロンプトを承認すればautoモードが再開します。この回数は設定で変更できません。`-p` を使う非対話モードでは、確認する人がいないためセッションが中断されます。

拒否された操作は `/permissions` の「Recently denied」タブに残り、`r` キーで手動承認による再実行ができます。

## 手動のまま使いたい場合

セッション中の切り替えは、CLIでは **Shift+Tab**、デスクトップアプリではモードのドロップダウンです。

既定を固定したい場合は、**ユーザー設定**（`~/.claude/settings.json`）の `permissions.defaultMode` を設定します。`"manual"` はv2.1.200以降で受け付けられます。プロジェクト側の `.claude/settings.json` に書いた `"auto"` は、リポジトリが自分自身にautoモードを許可できないようv2.1.142以降で無視される点にも注意してください。

組織単位で止める場合は、管理者がmanaged settingsで `permissions.disableAutoMode` を `"disable"` に設定します。

## 筆者の見方

Anthropic自身が「autoモードはプロンプトを減らすが安全性を保証するものではない」「本番インフラへの重大な変更には人のレビューを推奨する」と明記しています。数字を見るかぎり、承認疲れで機械的にOKを押す運用より分類器のほうが危険なコマンドを止めている、という主張には根拠があります。一方で見逃し率はゼロではありません。

現実的な落としどころは、**autoモードを受け入れたうえで、自分の環境で絶対に自動で通したくない操作だけ `permissions.ask` / `deny` に書き出しておく**ことだと考えます。8月14日より前に一度洗い出しておくと安全です。

なお、2026年8月8日リリースの v2.1.225 では、autoモードが自身の権限チェックに対する安全フィルタの拒否を「連続ブロック回数」に数えてしまう不具合が修正されています。更新状況は `claude --version` で確認できます。
