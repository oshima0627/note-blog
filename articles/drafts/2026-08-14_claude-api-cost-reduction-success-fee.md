# Claude API請求を削って売る：12の型と契約7論点

売り物を1行だけ変える話をします。「開発します」ではなく「御社のClaude API請求を、1リクエストあたりで下げます」です。

対象は、Claude Codeでコードベースは読めるのに、売り物が「開発できる」しかない人。手に入るのは3つです。コストが膨らむ12パターンの診断チェックリスト、Usage / Cost APIで作る「下がった」の証跡、そして揉めない契約条項の文案。値付けは二階建てで、本記事では「初期診断10万〜30万円＋削減額の20〜30%」という数字を使います。

ただし、この数字は**筆者が提案する設計値です。業界相場ではありません。** 裏付ける公開相場は、本記事の調査範囲では確認できませんでした。ここを曖昧にしたまま読み進めないでください。

参照できる隣接相場だけ、先に置いておきます。フリーランスエンジニアの平均月単価は約80万円、平均時間単価は5,319円です（ファインディ株式会社 2026年3月11日発表、n=265、調査期間2026年1月23〜30日、https://findy.co.jp/3922/ ）。技術顧問の副業案件は週1日稼働で月20万円前後とされています（FLEXY掲載案件例・**二次情報**、https://flxy.jp/media/article/8443 ）。

つまり成果報酬型がこの実勢を上回るには、「1社あたり月10万円以上の削減を、3社以上で継続的に出す」水準が要ります。この記事は、そこから逆算した診断・計測・契約の型です。数値・仕様はすべて2026年8月14日時点の公式情報に基づきます。

## 1. この記事は誰のためか——対象読者と、狙える金額の「設計値」

先に読者を絞ります。

**読むべき人**

- Claude Codeでコードベースを読めるが、売り物が「開発できる」しかない人
- 単価が時間×人月から抜け出せず、稼働を増やす以外に伸ばし方がない人
- AI受託の価格競争を避けたい人。ココナラの生成AIカテゴリには「ChatGPT API連携」「GPTs制作」の同種出品が多数あります

**読まなくていい人**

- Claude APIを本番運用している企業に、接点が一切ない人

最後の条件は重要です。1社目は既存の関係から取るのが前提だからです。請求データという機微情報を見せてもらう商売なので、初対面では成立しません。

**収益モデル（3工程契約）**

- 第1工程: 初期診断フィー（固定）
- 第2工程: 改修実装（固定 or 時間）
- 第3工程: 計測レポート期間の削減額シェア

**金額の目安**

> 「初期診断10万〜30万円＋削減額の20〜30%」は筆者の設計値であり、業界相場ではありません。国内の成果報酬型コスト削減コンサル各社は、料率も報酬対象期間も公開していません。

この一文は、以降すべての金額表現に掛かります。

**初期コスト**

金銭はほぼゼロです。月あたり数千円程度の、自分の検証用API利用料だけを見込みます。公式ドキュメントもUsage / Cost APIも無料で使えます。

時間は次の内訳です。

- 診断キットの構築: 2〜3日
- チェックリストの整備: 1〜2日
- 契約テンプレートの作成: 2〜3日

合計でおおむね1〜2週間です。弁護士レビューを入れる場合は、別途費用と2週間程度を見込みます。

## 2. 誠実さの宣言——確認できたこと／確認できなかったこと

先に調査の限界を申告します。ここを曖昧にすると、以降の全部が信用できなくなるからです。**そして、この「確認できなかったリスト」は、そのまま商機の一覧でもあります。** 誰も数字を公開していない領域では、最初に型を作った人が基準になります。

**確認できたこと**

- Claude APIの単価、キャッシュ倍率、最小キャッシュ長、Batch割引、サーバーサイドツール課金、Usage / Cost APIの仕様。すべて2026年8月14日時点で platform.claude.com の公式ドキュメントで確認しました
- 成果報酬型コスト削減コンサルという業態は国内に実在します。プロレド・パートナーズ、レイヤーズ・コンサルティング、ピュアグロース、ウィザーズプラスなどです。ただし対象は通信費・物流費・家賃等の間接費です

**確認できなかったこと（重要）**

- 削減額シェア型でLLM APIコスト最適化を提供している国内サービス・事業者は、特定できませんでした。ですから本記事では「既にこういうサービスがある」とは書きません
  - 含意: 合わせるべき先行者の型がありません。自分の設計が、そのまま最初の型になります
- 成果報酬型コンサルの具体的な料率レンジ。上記4社はいずれも料率（％）も報酬対象期間もWebサイト上に公開していません。よって20〜30%という数値に、公開相場の裏付けはありません
  - 含意: 比較される相場が存在しません。自分の算定式を、そのまま提案に持ち込めます
- 報酬対象期間の業界標準、初期費用の相場
  - 含意: 業界標準がないので、第12節の条項をそのまま「自分の標準」として先に提示できます

  - 含意: 自分の実測1本が、そのまま希少な一次情報になります
- 「LLM運用コストの◯%が無駄」といった、検証済みの統計
  - 含意: 割合で語れる人がいません。実測で語れる人が、そのぶん強く出られます

**使わないと決めたもの**

英語圏の個人ブログやベンダー記事には、大幅な削減率を掲げた事例が流通しています。いずれも一次資料ではありません。ですから本記事では、その種の数値を一切使いません。

**書かないもの**

架空の顧客事例と体験談です。実測値は筆者が提示するものではなく、**読者がこれから自分で作るもの**という立て付けにしています。

そして全料金数値には「2026年8月14日時点・最新は公式で要確認」を付し、公式URL（ https://platform.claude.com/docs/en/about-claude/pricing ）を併記します。

## 3. なぜ今この商売が成立するのか——86.4%が使い、27.0%が「組織的な取組はない」

市場の存在を、一次統計だけで示します。

総務省の令和8年版情報通信白書（2026年7月24日公表、https://www.soumu.go.jp/main_content/001082851.pdf ）によると、日本企業の生成AI利用率は86.4%です。2024年度の55.2%から大きく伸びました。活用方針ありも68.9%で、前年の49.7%から上昇しています。

一方、同じ白書に対照的な数字があります。「業務変革に組織的な取組はない」と答えた割合です。

- 日本: 27.0%
- 米国: 1.4%
- ドイツ: 4.9%
- 中国: 2.6%

調査は2026年1月〜2月に日米独中で実施されています。日本だけが桁違いです。

ここから読み取れることを、推測と明示したうえで書きます。導入率は高いのに管理体制が伴っていない企業が、日本には構造的に多いと考えられます。つまり「請求は立っているが、誰も分解していない」状態です。それがターゲットです。

海外の動きも見ておきます。FinOps Foundationの「State of FinOps 2026」（n=1,192、年間クラウド支出$83B超を代表、https://data.finops.org/ ）では、回答者の98%がAI支出を管理対象としています。2025年は63%、2024年は31%でした。「FinOps for AI」が2026年の最重要の将来課題に挙がり、AIコスト管理はチームに最も必要なスキルの1位です。

需要の性質をここで整理します。単価が下がっても、管理需要は拡大しています。この2つは別物です。混同すると、後述する第16節の判断を誤ります。

最後に決裁の構造です。「効率化します」という提案は決裁されません。「月◯万円の請求が下がります」は決裁されます。同じ作業でも、言い方ではなく計測方法を変えることで通り方が変わります。

## 4. 空いている交差点——ツールは「どこに使われたか」しか出さない

競合を正確に置きます。

**ツール層（実在）**

Anthropic公式のUsage and Cost APIページには、パートナーとしてCloudZero / Datadog / Grafana Cloud / Honeycomb / Vantageが掲載されています。OSS / SaaSではLangfuse（ClickHouseが買収）、Helicone、LangSmithがあります。

**大手クラウド**

Google Cloudは2026年にSpend CapsとAIコスト可視化、FinOps Explainabilityエージェントを発表しています。Microsoft AzureもFinOpsソリューションを提供しています。

ここまでは埋まっています。埋まっていないのは次の4つです。

**断絶1: 可視化と改修の間**

可視化ツールは「どこに使われたか」を出します。ですが「どこを直せばいくら下がるか」は出しません。そして改修まで手を動かす人がいません。

**断絶2: コンサルとエンジニアの間**

成果報酬型コスト削減コンサルの公表資料では、LLM API費を費目に掲げる事業者を確認できませんでした。一方エンジニアは、成果報酬契約の型を持っていません。この交差点が空いている可能性があります。

**断絶3: 日本語の一次情報の薄さ**

キャッシュの最小長がモデル世代で単調でないこと。Claude 4.7以降は新トークナイザで同一文字列が約30%多いトークンになること（増加率は内容とワークロードの形で変わる、と公式は注記しています）。こうした落とし穴を、基準日つきで書いた日本語記事が見当たりません。国内の「LLM APIコスト削減」解説記事は技術Tips列挙で止まり、価格改定日や公式単価の基準日が書かれていないものが目立ちます。

**断絶4: 契約雛形の不在**

「削減額の定義・計測方法・報酬対象期間」の雛形が公開されていません。ここが本記事で最も価値のある部分です。

なお名称について1点。日本語圏には、これと紛らわしい略語が既にあります。生成AI検索対策（AIO / SEO文脈）を指す語です。混同を避けるため、本記事ではその略語を使わず、「LLM APIコスト最適化」または「AI FinOps」と呼びます。

ここから約1,800字、単価と割引の数字が続きます。いま暗記する必要はありません。**後半の診断も契約条項も、すべてこの節の数字の上に立ちます。**「どこに何が書いてあるか」だけ掴んで、案件が来たら戻ってきてください。この節だけをブックマークして使える密度にしてあります。

## 5. 商品の土台になる事実——2026年8月14日時点の公式単価と割引の仕組み

この節で押さえるのは4つです。モデル単価／キャッシュの倍率と最小長／Batchの50%オフ／長コンテキストの非割増。診断で毎回使うのは、実質2つだけです。**キャッシュ読取は入力の0.1倍。Batchは入出力とも50%オフ。** 残りは案件ごとに引きに来る数字です。

以降の診断も契約も、すべてここに載ります。基準日つきで一箇所にまとめます。

**全数値の基準日: 2026年8月14日時点。出典 https://platform.claude.com/docs/en/about-claude/pricing 。最新は公式で要確認です。**

### モデル単価（1Mトークンあたりドル）

表記の順序は「入力 / 5分キャッシュ書込 / 1時間キャッシュ書込 / キャッシュ読取 / 出力」です。

- Claude Opus 5: $5 / $6.25 / $10 / $0.50 / $25
- Claude Opus 4.8: Opus 5と同一（$5 / $6.25 / $10 / $0.50 / $25）
- Claude Sonnet 5: $2 / $2.50 / $4 / $0.20 / $10
- Claude Sonnet 4.6: $3 / $3.75 / $6 / $0.30 / $15
- Claude Haiku 4.5: $1 / $1.25 / $2 / $0.10 / $5
- Claude Fable 5: 入力$10 / 出力$50（最上位。コスト最適化の文脈では原則対象外）

ここで1つ、後の契約設計に効く事実を挟みます。Sonnet 5の$2/$10は、当初「2026年8月31日までの導入価格」として発表されました。ですがこれは公式に恒久価格化され、2026年9月1日予定だった$3/$15への引き上げは行われません（公式ページ注記）。

**値下げが実際に起きる市場である**という実例です。第11節の「自然減の除外」でこの事実を再利用します。

### プロンプトキャッシュ

出典: https://platform.claude.com/docs/en/build-with-claude/prompt-caching

- 5分TTL書込: 基本入力単価の1.25倍
- 1時間TTL書込: 基本入力単価の2倍
- キャッシュ読取（ヒット）: 基本入力単価の0.1倍

**損益分岐は公式に明記されています。5分TTLは読取1回、1時間TTLは読取2回で元が取れます。**

読取が入力単価の0.1倍という点は、逆から読むべきです。同じプレフィックスを再送しているのにキャッシュが効いていなければ、その分は10倍払っている計算になります。

### Batch API

出典: https://platform.claude.com/docs/en/build-with-claude/batch-processing

割引は入力・出力とも50%オフです。適用後の単価は次のとおりです。

- Opus 5: 入力$2.50 / 出力$12.50
- Sonnet 5: 入力$1 / 出力$5
- Haiku 4.5: 入力$0.50 / 出力$2.50

制約も正確に押さえます。

- 大半のバッチは1時間未満で完了します
- 結果は全件完了時、または24時間経過時の早い方で取得できます
- 24時間以内に完了しないバッチはexpireします。expiredしたリクエストは課金されません
- サイズ上限は1バッチあたり10万リクエストまたは256MBの、先に到達した方です
- 結果の保持は作成から29日間です

非対応パラメータは stream / speed / store / previous_thread_event_id / cache_hint / context_hint / max_tokens:0 / research_preview_2026_02 です。それ以外はベータ機能を含めほぼ全対応です。なお**Managed AgentsにはBatch割引が効きません**（公式明記）。

**プロンプトキャッシュ割引とBatch割引はスタックします。**ただしバッチは5分以上かかりうるため、共有コンテキストがある場合は1時間TTLキャッシュの方がヒット率が高い、と公式は推奨しています。

### 長コンテキスト

Claude 4.6以降は、1Mトークンのコンテキストウィンドウ全体が標準価格です。長コンテキスト割増はありません。公式は「90万トークンのリクエストは9千トークンのリクエストと同じ単価」と明記しています。キャッシュ・バッチ割引も全域に標準適用されます。

ここから言えることは1つです。「長文だから高い」は単価の問題ではありません。単に送っているトークンが多い、という設計の問題です。

## 6. 【診断チェックリスト前半】キャッシュが無言で死ぬ6パターン

ここからが記事の核その1です。

12個を順に潰す必要はありません。**現場で最初に見るのは3つです。パターン1（cache_readが常に0）、パターン10（inference_geoとFast modeの不要指定）、パターン12（そもそも計測していない）。** この3つは、コードを深く読まなくてもレスポンスと設定だけで判定でき、しかも当たれば効きが大きい。残る9個は、この3つを潰したあとで順に見ます。

先に前提を注記します。以下は「公式仕様から論理的に導ける典型パターン」です。「日本企業のN%が該当」といった統計は確認できませんでした。ですから割合も削減率も書きません。各パターンは「症状 → なぜ課金が増えるか → コード上でどう見つけるか」の3点で統一します。

**パターン1: キャッシュ未使用のフルコンテキスト送信**

- 症状: 毎リクエストで同じシステムプロンプトと同じ資料を丸ごと送っている
- なぜ増えるか: 読取は入力単価の0.1倍です。同一プレフィックスを再送しているのに `cache_read_input_tokens` が0なら、その分は10倍払っている計算になります
- 見つけ方: レスポンスの `cache_read_input_tokens` をログに出し、常に0の経路を探します

まずこれをログに落とします。診断はここから始まります。

```python
# 全リクエストの応答からキャッシュ関連トークンを記録する
usage = response.usage
print({
    "input": usage.input_tokens,
    "cache_create": usage.cache_creation_input_tokens,
    "cache_read": usage.cache_read_input_tokens,
    "output": usage.output_tokens,
})
```

`cache_create` だけが立ち続け `cache_read` が0のままなら、書き込んでは捨てています。これは最悪の状態です。書込は1.25倍または2倍なので、キャッシュを使わないより高くなります。

**パターン2: サイレント無効化**

- 症状: キャッシュを設定したのに `cache_read_input_tokens` がほぼ0
- なぜ増えるか: キャッシュはプレフィックスの完全一致で判定されます。1バイト違えば、それ以降すべてが無効になります
- 見つけ方: システムプロンプトの組み立て経路を遡り、次の要素を探します

無効化の原因になる典型は次のとおりです。

- システムプロンプト先頭への現在時刻の埋め込み
- UUID、セッションID、ユーザー名の埋め込み
- `json.dumps` を `sort_keys` なしで使っている箇所
- `set` をイテレートして文字列化している箇所
- ユーザーごとにツールセットを変えている実装

コードベースを開いたら、まずこれを探します。

```bash
# システムプロンプト構築付近に混入しがちな非決定要素を洗う
grep -rn "datetime\|uuid4\|time.time()\|session_id" --include="*.py" ./src
grep -rn "json.dumps" --include="*.py" ./src | grep -v "sort_keys"
```

該当したら、可変部分をプレフィックスの**末尾**へ移します。先頭に置いてはいけません。

**パターン3: レンダリング順の無視**

- 症状: 会話の途中からキャッシュが効かなくなる
- なぜ増えるか: レンダリング順は tools → system → messages です。tools が先頭に来るため、会話途中でのツール追加・並べ替え・モデル切替はキャッシュを全損させます
- 見つけ方: ツール配列を動的に組み立てている箇所と、ターン途中でモデルを切り替えている分岐を探します

**パターン4: 最小キャッシュ長割れ**

- 症状: 設定は正しいのにキャッシュされない
- なぜ増えるか: 最小長未満のプレフィックスは、**エラーを返さずキャッシュされません**。無言で失敗します
- 見つけ方: レスポンスの `cache_creation_input_tokens` / `cache_read_input_tokens` を見るしかありません

最小キャッシュ長はモデルごとに異なります。

- 512トークン: Opus 5 / Fable 5 / Mythos 5
- 1,024トークン: Opus 4.8 / Sonnet 5 / Sonnet 4.6 / Sonnet 4.5
- 2,048トークン: Opus 4.7 / Haiku 3.5
- 4,096トークン: Opus 4.6 / Opus 4.5 / Haiku 4.5

閾値が世代で単調でない点が最大の落とし穴です。モデルを更新した途端に、キャッシュが突然効く、あるいは突然効かなくなります。ここは診断項目として必ず入れます。

**パターン5: 20ブロックのルックバック窓**

- 症状: エージェントループの2ターン目以降でキャッシュが外れる
- なぜ増えるか: 各ブレークポイントは、最大20コンテントブロックしか遡って既存キャッシュを探しません
- 見つけ方: `tool_use` / `tool_result` の往復回数を数えます。1ターンで20を超えていれば、次のリクエストは無言でミスします

**パターン6: 並列リクエストの同時発火**

- 症状: 並列化した途端に請求が跳ねる
- なぜ増えるか: キャッシュエントリは、最初のレスポンスがストリーミングを開始して初めて読めます。同一プレフィックスでN本を同時に投げると、全部が満額課金になります
- 見つけ方: 同一プレフィックスで並行実行している箇所を探します。1本投げて最初のトークンを待ってから、残りを流す形に直します

**補足仕様（診断で必ず確認する2点）**

- ブレークポイント上限は1リクエストあたり最大4つです。自動キャッシュ（トップレベルの `cache_control`）は1枠を消費します。5つ目を明示指定すると400エラーになります
- TTLの起点は、キャッシュを書込／読取するリクエストの「開始時点」です。レスポンス生成時間もTTLを消費します。4分かかるストリーミング応答なら、次のリクエストは応答完了から約1分以内に開始する必要があります。なおキャッシュを使うたび、追加費用なしでTTLは延長されます

## 7. 【診断チェックリスト後半】モデル選定・Batch・隠れ課金の6パターン

前節から連番で続けます。金額はすべて2026年8月14日時点の公式値です（ https://platform.claude.com/docs/en/about-claude/pricing ）。

**パターン7: Opus常用**

Opus 5の出力単価は、Haiku 4.5の5倍（$25 vs $5）、Sonnet 5の2.5倍（$25 vs $10）です。分類・抽出・整形といった、判断の要らない工程がOpusで動いていないかを見ます。ここは効きが大きい反面、最も事故りやすい箇所でもあります（第12節の品質ガードレールへ続きます）。

**パターン8: 非同期でよい処理を同期実行**

Batch APIの50%オフを使っていない状態です。夜間バッチ、評価実行、大量分類が代表的な候補です。レイテンシ要件があるのかを、機能ごとに確認します。

**パターン9: リトライとループの上限なし**

- 429 / 5xx の再試行が無制限になっていないか
- エージェントループの反復上限が未設定でないか
- `max_tokens` 不足による途中切れが、丸ごと再実行を生んでいないか

3つ目は見落とされがちです。切れた分も課金されているうえ、やり直しで二重に払っています。

**パターン10: 不要なプレミアム**

要件がないのに `inference_geo:"us"` を指定すると、入力・出力・キャッシュ書込・読取のすべてに1.1倍の乗数が掛かります（Claude 4.6以降）。`global`（デフォルト）は標準価格です。データレジデンシー要件がなければ、指定を外すだけで1.1倍が外れます（約9%の削減）。

Fast modeも同様です。Opus 5 / Opus 4.8で$10/$50、つまり標準の2倍です。リサーチプレビューであり、Claude API（ファーストパーティ）のみで使えます。Batch APIとは併用できません。さらにキャッシュ倍率とデータレジデンシー倍率は、fast mode価格の上に重ねて適用されます。

**パターン11: サーバーサイドツールの野放し**

トークン費用とは別建ての課金があります。

- `web_search`: $10 / 1,000検索。1検索=1課金です（結果件数に関係なく）。エラー時は非課金です
- `web_fetch`: 追加課金はありません。取得内容のトークン費用のみです。`max_content_tokens` で暴発を防げます。目安は一般的なWebページ10kB≒2,500トークン、大きなドキュメント100kB≒25,000トークン、論文PDF 500kB≒125,000トークンです
- `code_execution`: `web_search` / `web_fetch` と併用時は無料です。単独利用時は実行時間課金で、組織あたり月1,550時間が無料、超過分は$0.05/時間/コンテナです。実行時間は最低5分から計上され、ファイルを含むリクエストはツールが呼ばれなくても課金されます

`web_fetch` の上限未設定は特に危険です。論文PDF1本で125,000トークン相当が流れ込みます。

**隠れコスト: tool定義のトークン**

ツールを1つでも渡すと、ツール用システムプロンプトが自動付与されます。Opus 5では `tool_choice` が auto / none のとき286トークン、any / tool のとき406トークンです。加えてbashツールは追加325トークン（Opus 5 / 4.8 / 4.7）、text_editor（`text_editor_20250429`）は追加700トークンです。

使っていないツールを渡し続ける実装は、毎リクエストこれを払っています。ツール棚卸しは、削減施策として単独で成立します。

**隠れコスト: Managed Agents**

トークン課金に加えて、セッション実行時間が$0.08/セッション時間かかります。statusがrunningの間だけミリ秒単位で計上され、idle / rescheduling / terminated は非計上です。加えてBatch割引が効きません。

**パターン12: 計測していない**

Usage / Cost Admin APIが未使用、ワークスペース分離なし、スペンドリミット未設定。どの機能がいくら使っているかが、社内の誰にも分かりません。

**これが最初に直すべき点であり、同時に成果報酬の証跡が作れないという意味で、受注の前提条件でもあります。**

> 請求の分解ができて初めて、成果報酬の証跡が作れます。ここが受注の前提条件です。次節から、この12項目の判定を半日で終わらせる方法に移ります。

## 8. Claude Codeで診断を機械化する——12パターンを監査コマンドに落とす

12パターンを頭で覚えて毎回手作業でやると、1案件の診断に数日かかります。それでは単価が上がりません。チェックリストに落として、Claude Codeのカスタムコマンドにします。

**監査項目（a）〜（h）**

- (a) `cache_read_input_tokens` が常に0の経路を探す
- (b) システムプロンプト内の datetime / uuid / セッションID を grep する
- (c) tools配列の構築が非決定的でないか（`json.dumps` の `sort_keys`、`set` のイテレート、ユーザー別ツールセット）
- (d) プレフィックスがモデル別最小キャッシュ長（512 / 1,024 / 2,048 / 4,096）を超えているか
- (e) 判断不要な工程がOpusで動いていないか
- (f) 非同期化できる処理がBatch未使用でないか
- (g) `inference_geo` / Fast mode の不要指定がないか
- (h) `web_search` / `web_fetch` / `code_execution` の上限設定があるか

これをMarkdownの監査チェックリストとして固定資産化します。骨格はこれで足ります。

```markdown
# LLM APIコスト監査チェックリスト（基準日: 2026-08-14）

## A. キャッシュ
- [ ] a. cache_read_input_tokens が常に0の呼び出し経路
- [ ] b. system先頭の datetime / uuid / session_id
- [ ] c. tools配列の非決定的構築（sort_keys / set / ユーザー別）
- [ ] d. プレフィックス長 < モデル別最小長（512/1024/2048/4096）
- [ ] e. ブレークポイントが5つ以上、または20ブロック超のループ

## B. モデルと実行形態
- [ ] f. 判断不要な工程が Opus で実行されている
- [ ] g. 非同期化可能な処理が Batch 未使用
- [ ] h. inference_geo:"us" / Fast mode の要件なし指定

## C. ツールと計測
- [ ] i. web_search / web_fetch / code_execution の上限未設定
- [ ] j. 未使用ツール定義の常時添付
- [ ] k. Usage/Cost API 未使用・ワークスペース未分離・スペンドリミット未設定

## 出力形式（必須）
各指摘は「指摘 / 該当ファイル:行 / なぜ課金が増えるか」の3点で書く。
削減率の数値は書かない。実測は別工程で行う。
```

これをClaude Codeのカスタムコマンドとして登録します。

```markdown
---
description: LLM APIコストの監査を実行する
---

`docs/llm-cost-audit-checklist.md` を読み込み、このリポジトリを監査してください。

手順:
1. Claude API を呼び出している箇所をすべて列挙する
2. 各呼び出しについて、チェックリストのA〜Cを順に判定する
3. 該当した項目のみ「指摘 / ファイル:行 / なぜ課金が増えるか」の3点で出力する

制約:
- 削減率・削減額の数値を推定して書かないこと
- 該当が確認できない項目は「未確認」と書き、推測で埋めないこと
```

**成果物の設計が肝心です**

監査の出力を「指摘一覧」で終わらせてはいけません。「指摘＋該当ファイル/行＋想定削減の効き方」の形にします。そうすると、顧客に出す提案書の素材がそのまま出てきます。営業資料と納品物が同じ工程から出る状態を作ります。

**工数の目安**

チェックリストの整備に1〜2日を見込みます。狙いは、1案件あたりの診断工数を数日から半日〜1日に落とすことです。ここが成果報酬の採算を決めます。

**重要な注意**

監査結果に削減率の数値を機械的に書かせてはいけません。削減率は実測（第9節）で出すものです。診断段階で数値を約束すると、後で自分の首を絞めます。カスタムコマンドの制約に、この禁止を明示的に書いておきます。

ここまでが「どこが無駄か」の特定です。次は「いくら下がったか」の証明に移ります。API仕様の話になりますが、目的は1行です。**顧客に「下がりました」と言うための、第三者が見て納得する数字をどこから取るか。** 対応も1行で足ります。Usage APIが「トークンの内訳」、Cost APIが「実際にいくら払ったか」。細部は、コードを書く段になって戻れば十分です。

## 9. 計測の作り方——Usage API / Cost APIで「証跡」を作る

成果報酬は証跡がすべてです。証跡が作れなければ、報酬の請求ができません。

出典: https://platform.claude.com/docs/en/manage-claude/usage-cost-api （2026年8月14日時点）

### Usage API

- エンドポイント: `GET /v1/organizations/usage_report/messages`
- バケット幅: 1m / 1h / 1d
- 計測対象: 未キャッシュ入力・キャッシュ読取・キャッシュ作成・出力を個別に計測できます
- フィルタ・グループ化: model / workspace / api_key / service_tier / context_window / inference_geo / speed（`speed` のみ `anthropic-beta: fast-mode-2026-02-01` ヘッダが必要です）
- 粒度上限: 1mは最大1,440バケット、1hは最大168、1dは最大31

### Cost API

- エンドポイント: `GET /v1/organizations/cost_report`
- 通貨: USD建て（セント単位の文字列で返ります）
- 粒度: 日次のみ
- グループ化: workspace_id / description。descriptionでグループ化すると、modelやinference_geoがパースされて返ります

> **Cost APIの重要な穴**: Priority Tierのコストはこのエンドポイントに含まれません。ベースラインを作る際にここを見落とすと、後から差額が合わなくなります。

> **もう1つの穴**: `code_execution` のコストはCost APIに `Code Execution Usage` として現れますが、Usage APIには含まれません（公式FAQ）。第7節のパターン11で扱った費目なので、両APIの数字を突き合わせるときのズレ要因として先に押さえておきます。

> **もう1つの制約**: Claude Platform on AWSでは、Usage / Cost APIのプログラマティックアクセスが現時点で利用できません（Consoleのみ）。顧客がAWS経由なら、受注前に必ず確認します。

### 認証とデータの鮮度

認証にはAdmin APIキー（`sk-ant-admin01-...`）が必要です。通常のAPIキーとは別物です。スコープを指定でき、`read:analytics` や `read:spend_limits` などを1本のキーに組み合わせられます（ https://platform.claude.com/docs/en/manage-claude/admin-api-keys ）。Claude Enterprise（claude.ai）組織は、Analytics APIキーという別系統になります。

データはリクエスト完了から概ね5分以内に反映されます。継続的なポーリングは毎分1回が推奨です（ページネーション取得のような短時間のバーストは、より高頻度でも許容されます）。

### 診断キットを作る

自分のAnthropic組織でAdmin APIキーを発行し、両APIを叩くスクリプトをClaude Codeに書かせます。**キーは必ず環境変数から読みます。ハードコードは禁止です。**

```python
import os, requests

KEY = os.environ["ANTHROPIC_ADMIN_KEY"]  # sk-ant-admin01-... を環境変数から
BASE = "https://api.anthropic.com/v1/organizations"

def usage_by_model(start: str, end: str):   # 例: "2026-07-01T00:00:00Z"
    r = requests.get(
        f"{BASE}/usage_report/messages",
        headers={"x-api-key": KEY, "anthropic-version": "2023-06-01"},
        params={
            "starting_at": start,
            "ending_at": end,
            "bucket_width": "1d",
            "group_by[]": "model",
        },
    )
    r.raise_for_status()
    return r.json()
```

期間は `starting_at` / `ending_at` にISO-8601形式（末尾 `Z`）で渡します。Cost API側も同じ形です。`description` でグループ化すると、modelやinference_geoが分解されて返ります。

```python
def cost_by_description(start: str, end: str):   # 例: "2026-07-01T00:00:00Z"
    r = requests.get(
        f"{BASE}/cost_report",
        headers={"x-api-key": KEY, "anthropic-version": "2023-06-01"},
        params={
            "starting_at": start,
            "ending_at": end,
            "group_by[]": "description",
        },
    )
    r.raise_for_status()
    return r.json()  # USD建て・セント単位の文字列で返る
```

出力はCSVとグラフまでを1コマンドにまとめます。model / workspace / service_tier / context_window でグループ化し、未キャッシュ入力・キャッシュ読取・キャッシュ作成・出力を分けて日次で出します。

**この設計の意味**

顧客に見せられる「請求分解レポート」の雛形ができます。営業で見せる資料と、納品する成果物が同一になります。作るのは1回、使うのは全案件です。

証跡ができました。**証跡がないうちは、次節以降の契約はどれも書けません。** ここからは、その数字を報酬に変える条項の話です。

## 10. ベースラインの固定——ここを外すと成果報酬は必ず壊れる

改修に着手する前に、必ずベースラインを固定します。

**手順**

改修着手前の直近30〜90日を、Cost APIの日次データで固定します。workspace / model / description 別に分解し、書面に添付します。口頭合意で進めてはいけません。

**主指標は絶対額にしない**

主指標は「処理量あたり単価」に置きます。次のいずれかです。

- 1リクエストあたりUSD
- 1処理あたりUSD
- 1ユーザーあたりUSD

理由は第11節で詳述します。

**トークナイザ差という地雷**

Claude 4.7以降のモデルは新トークナイザを使用します。同一テキストで**約30%多いトークン**を生成します（公式注記）。増加率は内容とワークロードの形で変わる、と公式は注記しています。だからこそ、後述の再ベースラインが要ります。Sonnet 4.6以前は旧トークナイザです。

帰結は深刻です。新モデルへ移行すると、単価が下がっても請求が下がらない、あるいは増えることがあります。

> **旧モデルの実績値を、そのまま新モデルのベースラインに使ってはいけません。**削減額の計算が根本から壊れます。

対処は1つです。`count_tokens` で再ベースラインを取ります。

```python
import os, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
text = open("sample_prompt.txt").read()

for model in ["claude-sonnet-4-6", "claude-opus-5"]:  # 旧/新トークナイザの比較
    n = client.messages.count_tokens(
        model=model,
        messages=[{"role": "user", "content": text}],
    )
    print(model, n.input_tokens)
```

差が出たら、それはモデル移行によるトークン増であって、削減施策の失敗ではありません。モデルを跨ぐ比較は「トークン数」ではなく「処理1件あたりのUSD」で行います。

**施策は1つずつ入れる**

改修はまとめて入れてはいけません。キャッシュ導入、モデル降格、Batch化、ツール棚卸し。この4つを同時に入れると、どれが何%効いたかを説明できなくなります。成果の帰属が説明できない状態は、成果報酬にとって致命的です。

**自分の実測を作る意義**

国内に数値つきの公開事例が乏しいことは、第2節で書いたとおりです。裏を返せば、自分の実測値そのものが希少な資産になります。顧客名を伏せ、自分のプロダクト分だけでも構いません。1本作れば、それが営業資料になります。

## 11. 契約設計（前半）——削減額の定義・ベースライン・自然減の除外

ここが記事の核その2です。成果報酬型は、契約が商品そのものです。

**大前提: 契約テンプレートは案件を取る前に作ります。**案件が来てから書くと、必ず妥協します。

なお、以下の条項案は**叩き台であり、法的助言ではありません。**実際に使う前に弁護士レビューを受けることを推奨します。

### 論点1: 削減額の定義

絶対額を指標にしてはいけません。月額請求額そのものを指標にすると、2つの事故が起きます。

- 利用が伸びた場合: 削減が出ているのに請求は増えます。報酬がゼロになります
- 利用が落ちた場合: 何もしていないのに請求が減ります。受け取ってはいけない報酬が発生します

どちらも関係を壊します。ですから「処理量あたり単価」で定義し、分子と分母を契約書に明記します。

**条項の文案（削減額の定義）**

> 第〇条（削減額の定義）
> 1. 本契約における「単位コスト」とは、対象期間中に甲のClaude API利用に生じた費用（USD建て）を、当該期間中の【対象処理件数】で除した値をいう。
> 2. 前項の分子は、Cost API（`/v1/organizations/cost_report`）により取得した、対象ワークスペース〇〇に係る費用の合計とする。
> 3. 前項の分母は、【　　　　】（例: 対象機能のリクエスト件数／処理完了件数／月間アクティブユーザー数）とし、甲乙双方が参照可能な計測系から取得する。
> 4. 「削減額」とは、（基準単位コスト − 対象月の単位コスト）に当該月の分母実績を乗じた額をいう。
> 5. 乙の報酬は、前項の削減額に料率〇%を乗じた額とする。

料率について、繰り返します。本記事で示す料率は**筆者の設計案であり、業界相場ではありません。**

### 論点2: ベースライン

第10節の手順を、そのまま条項にします。

- 改修着手前の直近30〜90日を対象期間とする
- Cost APIの日次データで固定する
- workspace / model / description 別に分解し、別紙として書面添付する

別紙添付が要です。数字を本文に埋めると、後から差し替えができません。

### 論点3: 自然減の除外（最大の地雷）

モデルの値下げや新モデル投入による単価改定は、**自分の成果ではありません。**

これは机上の懸念ではありません。第5節で書いたとおり、Sonnet 5は$2/$10が恒久価格化され、2026年9月1日に予定されていた$3/$15への引き上げが撤回されました。放っておいても請求が下がる市場です。

この状況で、モデル値下げによる請求減を自分の成果として請求したらどうなるか。信頼を一発で失います。

**条項の文案（単価改定時のベースライン再計算）**

> 第〇条（提供元の単価改定に伴う調整）
> 1. 本契約の期間中に、Anthropic社が対象モデルの課金単価を改定した場合、甲乙は、改定日の属する月の初日をもって基準単位コストを再計算するものとする。
> 2. 前項の再計算は、基準期間中の実績トークン量（未キャッシュ入力・キャッシュ書込・キャッシュ読取・出力の別を維持する）に、改定後の単価を乗じて行う。
> 3. 前項により生じた単位コストの低下分は、乙の成果に計上しない。
> 4. 単価改定の事実は、Anthropic社の公式価格ページの記載をもって確認する。

第2項の書き方が重要です。トークン種別ごとに単価が違うため、種別を潰して合算すると再計算が狂います。

そして、この条項を**自分から提案すること**を勧めます。顧客が最も警戒するのは「AIが勝手に安くなった分まで請求されるのでは」という点だからです。先に自分で塞ぐと、それがそのまま信頼獲得の手段になります。

> 契約テンプレートは1度作れば全案件で使えます。もしあなたが顧客側の立場なら、ここまでの条項のどこに一番引っかかるでしょうか。**引っかかった箇所をコメントで教えてください。** それが、次に潰すべき論点です。同じテーマで実測と続報を書いていくので、フォローしておくと届きます。

## 12. 契約設計（後半）——期間・通貨・品質ガードレール・計測主体

### 論点4: 報酬対象期間

無期限は必ず揉めます。改修完了後3ヶ月／6ヶ月／12ヶ月のいずれかで区切り、月次で確定させます。

「年間削減額の◯%」方式にする場合は、年間の定義を明記します。12ヶ月分の実績を合算する実測方式なのか、月次×12の推計方式なのか。ここを書かないと、支払時期の解釈が割れます。

**条項の文案（報酬対象期間）**

> 第〇条（報酬対象期間）
> 1. 乙の成果報酬の対象期間は、改修完了確認日の翌月1日から起算して【3／6／12】ヶ月間とする。
> 2. 削減額は暦月ごとに確定させ、翌月末日までに甲乙が書面（電磁的記録を含む）で相互確認する。
> 3. 前項の確認をもって当該月の報酬額は確定し、以後の遡及的な変更は行わない。ただし計測系の明白な誤りが判明した場合はこの限りでない。
> 4. 対象期間の満了後、乙は本条に基づく報酬を請求しない。

第3項の「遡及的な変更は行わない」が実務上効きます。これがないと、期末に全月分を蒸し返されます。

### 論点5: 通貨

Anthropicの請求はUSDです。円建て報酬にすると、為替で削減額が上下します。自分の成果と無関係な変動を報酬に持ち込んではいけません。

USD建てで削減額を定義し、支払時の適用レート（基準日と参照する為替情報源）を固定する条項を置きます。

### 論点6: 品質のガードレール

最も起こりやすい失敗は「Haikuに落として安くなったが、精度が落ちた」です。これは事故として最も痛い部類です。安くなった分を返しても、信頼は戻りません。

評価セットと合格ラインを契約に含めます。そして**合格しない削減は成果に計上しない**と定めます。

**条項の文案（品質ガードレール）**

> 第〇条（品質基準および成果の不計上）
> 1. 乙が提案する変更（モデル変更、プロンプト短縮、コンテキスト削減等）は、別紙〇に定める評価セットによる検証を経たうえで適用する。
> 2. 合格基準は、【変更前出力との一致率〇%以上】および【甲の業務部門が定める受入基準】の双方を満たすこととする。
> 3. 前項の基準を満たさない変更に起因する費用低下は、第〇条の削減額に計上しない。
> 4. 適用後に品質の低下が確認された場合、乙は速やかに変更を巻き戻し、当該期間の当該施策分は成果に計上しない。

実務としても押さえます。評価セットを組んでモデル降格後の品質劣化を検出できることは、この商売の必須スキルです。**評価セットのないモデル降格提案はしません。**

### 論点7: 計測主体

Cost APIのデータは、顧客の組織からしか取得できません。Admin APIキーが必要だからです。

選択肢は2つです。事前にどちらかを決めます。

- 顧客側で取得してもらい、エクスポートしたデータを受け取る
- 顧客の管理下で、読み取り専用スコープのキーを発行してもらう

## 13. 鍵を預からない——セキュリティ審査を通す運用設計

原則を1つだけ立てます。**顧客の本番APIキーは受け取りません。**

これは倫理の話ではなく、受注可能性の話です。鍵を預かる前提の提案は、顧客のセキュリティ審査で止まります。

根拠になる公式仕様が2つあります。

- APIキーは単一のワークスペースにスコープされ、そのワークスペース内のリソースにしかアクセスできません（ https://platform.claude.com/docs/en/build-with-claude/workspaces ）
- ワークスペース単位で月次のスペンドリミットとアラート閾値を設定できます。組織全体の上限より低い値を設定でき、高くはできません（ https://platform.claude.com/docs/en/manage-claude/spend-limits-api ）

この2つを使って、次の構成を提案します。

- 構成(a): 顧客組織内に専用ワークスペースを作ってもらい、そこにスコープされたキーだけを使う
- 構成(b): ワークスペース単位のスペンドリミットとアラートを設定する
- 構成(c): 請求データは、読み取り専用スコープのAdmin APIキー（`read:analytics` 等）、または顧客側が実行してエクスポートしたCSVで受け取る

運用面も詰めます。NDAと契約に上記を明記し、案件終了時のキー失効手順まで書きます。「終わったら消してください」では消えません。誰がいつ何を失効させるかを、手順として残します。

リスクは直視します。Admin APIキーは組織全体に効きます。通常のAPIキーより慎重に扱う必要があります。**漏洩したときの賠償リスクは、受託フィーを軽く超えます。**この非対称性を理解したうえで設計してください。

## 14. 成果報酬を断られたら——プランB（固定フィー診断／月額顧問／ハイブリッド）

成果報酬は嫌がられる場面が多くあります。理由は主に3つです。

- 削減額の証明コストが顧客側にもかかる
- 変動報酬の経理処理が面倒
- 社内で説明しづらい

ですからプランBを用意します。プランBを持っていること自体が、提案の通しやすさに効きます。

**プランB① 固定フィー診断のみ**

現状の請求分解、改修提案書、想定削減レンジの提示までを固定額で提供します。成果責任を負わないぶん、受注ハードルが下がります。そして実装フェーズへの入口になります。第8節と第9節の成果物が、そのまま商品になります。

**プランB② 月額顧問**

技術顧問・CTO顧問の副業案件は、月40万〜80万円／週2〜3日稼働が多いとされています。週1日稼働で月20万円前後、案件例では月10万円から160万円まで幅があります（FLEXY掲載案件例・**二次情報**、 https://flxy.jp/media/article/8443 ）。

コスト最適化に限定した薄い関与なら、下限帯（月10〜20万円／週1日以下）が現実的です。

**プランB③ 時間単価**

フリーランスエンジニアの平均時間単価は5,319円、平均月単価は約80万円です（ファインディ株式会社 2026年3月11日発表、n=265、https://findy.co.jp/3922/ ）。時間で売る形に戻すぶん、単価の上限もここで頭打ちになります。

**推奨: ハイブリッド**

診断フィーを固定で取り、削減額シェアは低めの料率にします。固定部分でキャッシュフローを確保し、成果部分でアップサイドを取ります。

**重要な警告: 成果報酬100%は、初期案件では避けてください。**削減余地の見立てを外したときに丸損になります。見立ての精度は、案件数を重ねないと上がりません。

そして提案の構造として、プランA（成果報酬）とプランB（固定）を並べて出します。並べること自体が、成果報酬案の通過率を上げます。選択肢が1つだと「やるか、やらないか」になりますが、2つあると「どちらにするか」になります。
