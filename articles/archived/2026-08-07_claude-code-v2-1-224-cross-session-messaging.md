# Claude Code v2.1.224：セッション同士がメッセージを送れるように

※本記事は2026年8月7日時点の公開情報にもとづきます。仕様・提供条件は変わりやすいため、最新は公式ドキュメントでご確認ください。

## この記事でわかること

- Claude Codeのセッション同士がメッセージをやり取りできるようになった件と、その要件
- 受け取り側で「届く／保留する／拒否する」を制御する設定
- 自前インフラでクラウドセッションを動かす「self-hosted environments」の位置づけ

2026年8月7日、Claude Code v2.1.224がリリースされました。追加された機能のうち大きいものは2つです。セッション間メッセージングと、自前インフラでクラウドセッションを実行する仕組みです。

## 1. セッション同士がメッセージを送れるようになりました

### 概要

これまで、別のターミナルで動いているClaude Codeに何かを伝えるには、自分でコピー&ペーストする必要がありました。v2.1.224からは、Claudeが別セッションのClaudeへ直接テキストを届けられます。

Claudeは2つのツールを使います。`ListAgents` で届く相手を探し、`SendMessage` で名前を指定して送ります。どちらも自分で呼ぶ必要はなく、Claudeが必要と判断したときに送ります。「別ターミナルのセッションにマイグレーションが終わったか聞いて」のように頼むこともできます。

届く相手は `/list-agents`（`/peers` でも可）で確認できます。セッションの名前は `/rename` コマンドや `--name` フラグで設定でき、未設定なら作業ディレクトリ名から自動で付きます。

### 送られるのはテキストだけです

やり取りされるのは、片方のClaudeが書いたプレーンテキストのみです。会話履歴やファイルは渡りません。会話ごと引き継ぎたい場合は、従来どおりセッションの再開（resume）を使います。

同じマシン内のやり取りは、セッションごとのソケット経由で行われ、Anthropicのサーバーを経由しないと公式ドキュメントに記載されています。一方、別マシンやWeb版のセッションとのやり取りはAnthropicのサーバーを経由し、しかも「返信のみ」です。こちらから会話を始めることはできません。

### 動作条件

公式ドキュメントに明記されている条件は次のとおりです。

- Claude Code v2.1.224以降が必要です
- 対応OSはmacOSとLinux（WSL 2内のLinuxを含む）です。ネイティブWindowsでは提供されません
- Amazon Bedrock、Claude Platform on AWS、Google CloudのAgent Platform、Microsoft Foundry経由では利用できません
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` などの環境変数で機能フラグ評価を切っていると、この機能も無効のままになります

条件を満たすセッションでは、有効化の操作は不要です。`/list-agents` が認識されない場合は、まず `claude --version` でバージョンを確認するのが公式の案内です。

## 2. 受け取り側の制御と安全面

### 届いたメッセージは「承認」にはなりません

受け取ったセッションのClaudeには、「これは自分（ユーザー）ではなく別セッションから来たメッセージだ」と伝えられます。そのうえで、以下の制限がかかると記載されています。

- 他セッションからのメッセージは、保留中の権限プロンプトへの同意にはなりません
- 権限設定や `CLAUDE.md` などの設定を、別セッションに言われたから変更することはしません
- メッセージ本文に `/compact` のようなコマンドが含まれていても、テキストとして届くだけで実行されません
- メッセージの内容を実行するのに権限が必要なら、通常どおり権限プロンプトが出ます

### 受信の挙動を決める設定

`crossSessionInbound` という設定で、届いたメッセージの扱いを選べます。値は3つです。

- `accept`: そのままClaudeに渡します
- `hold`: 通知だけ出して渡しません。後から許可されれば渡されます
- `refuse`: 渡さずに破棄します

明示的な値がない場合は、送信側と受信側の権限モードの組み合わせで自動的に決まります。受信側が権限プロンプトをバイパスしている場合は保留が既定で、送信側も同じくバイパスしているときだけ配信されます。保留時は承認ダイアログが出ます。このダイアログは `dialogExpiry` の期限（既定5分）を過ぎると閉じ、メッセージは破棄されます。

完全に止めたい場合は、受信を `crossSessionInbound: "refuse"` にし、送信側は `SendMessage` と `ListAgents` を権限のdenyルールに追加します。マシンをまたぐ送信に毎回承認を求めたい場合は、`isolatePeerMachines` を `true` にします。この設定は `bypassPermissions` モードでも承認を求めます。

なお、メッセージのループは自動的に止まる設計です。同一送信者からの繰り返しはレート制限され、短時間の同一メッセージは破棄されます。

## 3. self-hosted environments（Team/Enterprise向け）

もう1つの新機能が `claude self-hosted-runner` です。claude.aiやモバイル・デスクトップアプリ、スケジュール実行のルーチンから起動する「クラウドセッション」を、Anthropicのインフラではなく自社ネットワーク内のホストで実行できます。考え方はセルフホストのCIランナーと同じです。

公式ドキュメントによると、Team・Enterpriseプランのパブリックベータで、既定はオフです。Zero Data Retentionを有効にしている組織では利用できず、推論はAnthropic APIに固定されます。リポジトリのチェックアウトやビルド成果物は自社インフラに残りますが、会話そのものは推論のため `api.anthropic.com` に送られると明記されています。

個人利用のPro/Maxプランは対象外です。ただし「自分の常時起動マシンでClaude Codeを動かし、他のデバイスから操作したい」だけであれば、Pro/Maxでも使えるRemote Controlを使うよう公式ドキュメントが案内しています。

## 4. 個人開発者が見ておきたいその他の変更

v2.1.224のchangelogから、影響が出やすいものを挙げます。

- **サブエージェントの生成上限が撤廃されました**。1セッションあたり200体という上限がなくなりました。同時実行数と入れ子の深さの制限は引き続き適用されます
- **長いパスの不具合が修正されました**。200文字を超えるプロジェクトパスが、別プロジェクトのセッションディレクトリに解決されることがありました。セッション一覧・リネーム・fork・削除・`/resume` がプロジェクトをまたがなくなります
- **サンドボックスの拒否設定の抜け穴が修正されました**。`denyRead: "~/.aws/"` のように末尾スラッシュ付きで書いた拒否エントリが、LinuxとmacOSで黙って回避できる状態でした。該当する書き方をしている方は更新をおすすめします
- **サンドボックス違反の詳細がBashの結果に出るようになりました**。どのファイル・ネットワークアクセスがなぜ拒否されたかをClaudeが認識できます
- **フィードバック調査の共有内容が広がりました**。同意した場合、直前のリクエストのシステムプロンプト（`CLAUDE.md` の指示を含む）、ツール定義、モデルパラメータもアップロードされます。シークレットは従来どおり秘匿されるとされていますが、`CLAUDE.md` に社内固有の記述がある方は把握しておきたい変更です
- **`archive` プラグインソースが追加されました**。gitやnpmを介さず、HTTPS経由のzipからプラグインを導入できます。SHA-256でのピン留めも可能です

## 更新の確認方法

現在のバージョンは `claude --version` で確認できます。ネイティブインストール版はバックグラウンドで自動更新されます。すぐに反映したい場合は `claude update` を実行します。

一方、Homebrew・WinGet・apt・dnf・apkで導入した場合は既定で自動更新されません。`brew upgrade claude-code`、`winget upgrade Anthropic.ClaudeCode` のように、各パッケージマネージャの手順で更新します。Homebrewの `claude-code` caskはstableチャンネルを追跡するため、公式ドキュメントによると通常1週間ほど遅れて届きます。

## 筆者の見方

セッション間メッセージングは、複数ターミナルで並行作業している人ほど効きそうです。特にワークツリーを分けて同じリポジトリを触る場面では、片方の変更をもう片方に伝える手間が減ります。

一方で、受信側の挙動は権限モードの組み合わせで変わります。使う前に一度ドキュメントの受信制御の項を読んでおくと、「送ったのに届かない」で悩まずに済むはずです。
