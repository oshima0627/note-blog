# MCP新仕様2026-07-28でステートレス化：自作サーバーへの影響

2026年7月29日時点の情報です。仕様・対応状況は変わりやすいため、最新は各公式で確認してください。

2026年7月28日、MCP（Model Context Protocol：AIとツール・データソースをつなぐ共通規格）の新しい仕様リビジョン「2026-07-28」が公開されました。前回の「2025-11-25」からの変更で、プロトコルが**ステートレス**（各リクエストが独立して完結する形）になった点が最大の変更です。

同日、Anthropicも「この仕様への対応をClaude製品に展開していく」とする記事を公開しました。この記事によると、MCPのSDKは月間4億回超のダウンロードに達して年内で4倍に増加し、Claudeのコネクタディレクトリには950以上のMCPサーバーが掲載されているとされています。MCPサーバーを自作している人・使っている人に関係する内容なので、Claude Codeを使う立場から要点を整理します。

## この記事でわかること

- MCP 2026-07-28で何が変わったか（ステートレス化・通知・認可・拡張）
- 非推奨になった機能と、12ヶ月の移行期間ルール
- Claude / Claude Codeユーザーが今すべきこと（筆者の見方）

## 変更点1：ステートレス化（最大の変更）

公式の変更点一覧では、次の削除が「Major changes」として挙げられています。

- `initialize` / `notifications/initialized` のハンドシェイクを削除
- プロトコルレベルのセッションと、Streamable HTTPの `Mcp-Session-Id` ヘッダーを削除
- `tools/list` などの一覧系エンドポイントが接続ごとに異なる結果を返す仕組みを廃止

代わりに、各リクエストが `_meta` でプロトコルバージョンとクライアント能力（`io.modelcontextprotocol/protocolVersion`、`io.modelcontextprotocol/clientCapabilities`）を自分で運ぶ形になりました。バージョン不一致は `UnsupportedProtocolVersionError` が返ります。

また、サーバーが対応バージョン・機能・識別情報を返す `server/discover` というRPCが追加され、サーバーは**必須で実装する**とされています。呼び出し間で状態を保ちたいサーバーは、サーバーが発行したハンドルを通常のツール引数として渡す方式に移ります。

Anthropicの記事は、これによりサーバーをサーバーレスやエッジに置き、ロードバランサーの後ろで水平スケールさせられるようになると説明しています。

## 変更点2：通知とストリームの整理

- HTTP GETエンドポイントと `resources/subscribe` / `resources/unsubscribe` が、単一の長寿命ストリーム `subscriptions/listen` に置き換わりました
- SSEのストリーム再開・メッセージ再送（`Last-Event-ID`）が削除され、ストリームが切れたリクエストは新しいリクエストIDで再送する必要があります
- `ping`、`logging/setLevel`、`notifications/roots/list_changed` が削除されました。ログレベルは `_meta` の `io.modelcontextprotocol/logLevel` でリクエストごとに指定します

## 変更点3：MRTRとresultType

サーバーからクライアントへ問い合わせる従来の方式（`roots/list`、`sampling/createMessage`、`elicitation/create`）は、**MRTR（Multi Round-Trip Requests）**というパターンに置き換わりました。

サーバーは足りない情報を `inputRequests` に入れて `resultType: "input_required"` の結果を返し、クライアントは元のリクエストを再送する際に `inputResponses` で答える流れです。あわせて全結果に `resultType` が必須化されました。

## 変更点4：キャッシュ・ヘッダー・認可

- `tools/list` などの結果に `ttlMs`（鮮度のヒント）と `cacheScope`（`public` / `private`）が必須化され、クライアント側でキャッシュしてポーリングを減らせるようになりました
- Streamable HTTPのPOSTに `Mcp-Method` / `Mcp-Name` ヘッダーが必須化され、ゲートウェイやWAFがボディを解析せずルーティングできるようになりました
- 認可レスポンスに `iss` パラメータを含めることが推奨され、クライアントは受け取った `iss` を検証してから認可コードを引き換える必要があります（RFC 9207準拠）
- OAuth 2.0の動的クライアント登録（RFC 7591）が非推奨になり、Client ID Metadata Documentsが推奨方式になりました（未対応の認可サーバー向けに後方互換として残されます）

Anthropicの記事では、認可周りの整備により本番のOAuth 2.0 / OIDC構成に沿い、EntraやOktaのような企業向けID基盤と回避策なしでつながると説明されています。

## 変更点5：拡張フレームワーク（Apps / Tasks）

コア仕様を変えずに機能を足せる「Extensions」の枠組みが正式化され、2つの公式拡張が同時に公開されました。

- **MCP Apps**：サーバーがインタラクティブなHTML UIを提供し、ホスト側がサンドボックス化されたiframeで表示する仕組み
- **Tasks**：実験的なコア機能から拡張（`io.modelcontextprotocol/tasks`）へ移動。ブロッキングの `tasks/result` は `tasks/get` でのポーリングに置き換わりました

Anthropicの記事では、Claude側の新機能としてMCP Apps、ID基盤による管理者主導の認証、公開コネクタ向けの可観測性ダッシュボード、社内ネットワークのMCPサーバーを公開せずつなぐ「MCP tunnels」（リサーチプレビュー）が挙げられています。

## 非推奨になった機能と12ヶ月ルール

今回、機能の「Active / Deprecated / Removed」を定義し、**非推奨から削除まで最低12ヶ月**を確保する正式な廃止ポリシーが導入されました。非推奨になった主なものは次の通りです。

- Roots、Sampling、Logging（新規実装では採用しない方針。代替として、Rootsはツール引数やリソースURI・サーバー設定で渡す、SamplingはLLM APIに直接つなぐ、Loggingは標準エラー出力やOpenTelemetryを使う、と案内されています）
- HTTP+SSEトランスポート（2025-03-26から非推奨扱い。Streamable HTTPへ移行）

公式ブログは、これらは「今後も少なくとも12ヶ月は動く」としています。一方で、リビジョン2025-11-25そのものの終了日は明示されていません。

## SDKとClaude側の対応状況

公式ブログによると、Tier 1のSDK4種（TypeScript・Python・Go・C#）は公開時点で2026-07-28に対応済み、RustのSDKはベータ対応とされています。移行コストについては、特にセッションIDに依存していた開発者には発生するが、早期テストのフィードバックを取り込んで容易にした、と述べられています。

Claude製品側の対応は「近日中に順次展開」とされており、本稿執筆時点でClaude CodeがどのバージョンでMCP 2026-07-28に対応するかは、公式changelogでは確認できませんでした。

## Claude Codeユーザーへの影響（筆者の見方）

ここからは事実の整理ではなく、筆者の見方です。

第一に、Claude CodeでMCPサーバーを「使うだけ」の人が今日すべきことは、ほぼありません。クライアント側の対応はClaude Codeのアップデートで降りてくる話であり、変更点を把握しておけば十分だと考えます。

第二に、MCPサーバーを自作・運用している人は影響を受けます。特にセッションID前提の実装、`initialize` に依存した初期化、SSE再開に頼った長時間処理は作り直しが必要になります。12ヶ月の猶予はありますが、`server/discover` や `resultType` の必須化は「対応しないと新仕様のクライアントから使えない」種類の変更です。

第三に、Claude Codeの機能との関係で気になるのがRootsです。公式changelogによると、Claude Codeはv2.1.203（2026年7月7日）で「セッションの追加作業ディレクトリをMCP `roots/list` に載せ、変更時に `notifications/roots/list_changed` を送る」対応を入れています。新仕様ではこの通知が削除され、Roots自体も非推奨になりました。`/add-dir` で追加したディレクトリをMCPサーバーに伝える経路は、いずれ別の形に置き換わる可能性があると筆者は見ています。具体的な対応方針は未発表なので、公式の告知を待つのが確実です。
